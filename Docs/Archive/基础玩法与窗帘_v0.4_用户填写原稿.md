## 1. 基础玩法

### 1.1 玩家目标

玩家根据当前拍的操作提示，跟随 BGM 完成一段恶作剧。窗帘挑战中，先吸引 NPC 靠近，再包裹、左右挥打，最后完成甩出。

挑战内的基本循环：

> 看当前操作与下一步预告 → 做输入 → 判定成功则推进；漏拍则保留当前操作重试 → 连续漏拍过多，NPC 挣脱。

成功输入决定流程推进和成功演出；输入预反馈可以提前发生，但不能当成成功结算。上述漏拍重试与 NPC 挣脱是窗帘当前实例的策略，不默认强制所有未来编排采用同一结算策略。

### 1.2 通用基础输入库——按策划案

| 基础输入 | 策划定义／鼠标示范 | 窗帘当前应用 | Unity 状态 |
|---|---|---|---|
| A01 点按 | 区域内任意位置点按左键，表达一次短促动作 | 前两次吸引注意 | 已使用，但仍与窗帘脚本耦合 |
| A02 按住与松开 | 任意位置按住左键，再在提示时机松开；示范为圆环填满、变绿后松开 | 有持握衔接，但没有独立的按住计时／松开结算步骤 | 输入库定义已存在；独立模块尚未完成 |
| A03 定向移动 | 任意位置按住左键，复现示范方向；示范为向右滑，反馈达标后松开 | 包裹、左右挥、左下蓄力、右上甩出 | 已使用方向位移检测；窗帘不以松开作为成功条件 |
| A04 路径移动 | 任意位置按住左键，复现方向顺序；示范为先下再右，转向位置和下滑距离不固定，完成后松开 | 包裹步骤有“右→下”的编排，但当前是两个分别判定的 A03 步骤 | 不等于已经实现 A04 路径模块 |

连续点按、往返滑动、按住再拖动，是上述基础输入的重复或组合；“拉扯”“挥打”“蓄力”是具体表现，不新增成同级输入类型。自动演出属于流程步骤，不是第五种基础输入。

基础输入共同约定：示范圆球只用于演示与反馈，不是需要点击／抓住的目标。识别相对方向和顺序，不要求玩家沿固定线描画。网页基础输入示范尚未接入 BGM，不能把示范动画的秒数自动当成正式节拍规格；“快慢不限”指示范的空间识别，不代表音游中可以忽略时机。

**窗帘实例差异：** 当前窗帘不设独立松开判定，定向移动成功后可继续按住。网页示范的结束松手不能直接追加成窗帘的一拍；但也不能因此从通用输入库删除 A02。

## 2. 基础输入在窗帘中的当前落地规则——按 Unity

本节只记录窗帘实例，不覆盖或取代第 1 节策划案的完整输入库。未参与窗帘的 A02／A04，其尚未定的节奏规则不能由本节反推。

### 2.1 点按

| 项目 | 当前规则 |
|---|---|
| 触发 | 左键按下的瞬间 |
| 输入位置 | 在游戏画面中任意位置可以触发，不要求点中窗帘模型 |
| UI 排除 | 鼠标点中可交互 UI 按钮时，不把这次点击同时当作玩法输入 |
| 判定时刻 | 点击发生的这一帧，与当前目标拍比较 |
| 成功 | 在判定窗口内，播放成功反馈，推进一步，清零连续漏拍 |
| 太早 | 提示太早；保留当前操作；不缓存这次点击到目标拍 |
| 太晚 | 当前操作保留到下一目标拍重试，并计入漏拍 |
| 多次点击 | 当前没有通用点击冷却；成功后流程已经推进，后续点击可能作用于下一项点按步骤 |

#### 🟨 待填写 P02：连续点按处理

当前对照：没有通用点击冷却；下一步也是点按时，连续点击会继续参与下一步的判断。

### 2.2 按住＋定向移动

共同规则：

1. 按下左键，记录这次按下时的鼠标屏幕位置作为起点。
2. 按住期间，计算鼠标相对起点的累计位移，不以窗帘世界坐标作为起点。
3. 达到方向和距离条件后，进入“已准备”状态。
4. 保持左键按住；目标拍到达后，在有效窗口中结算成功。
5. 成功后将当前鼠标位置设为下一动作的新起点，清掉本次准备状态；可以不松手。

| 方向 | 代码识别条件 |
|---|---|
| 右 | 水平位移 ≥ 水平距离阈值 |
| 左 | 水平位移 ≤ −水平距离阈值 |
| 下 | 竖直位移 ≤ −竖直距离阈值 |
| 左下 | 同时达到向左和向下的距离阈值 |
| 右上 | 同时达到向右和向上的距离阈值 |

当前没有角度锥检测，不判断鼠标速度，也不要求描线。左／右动作只检查水平分量，不限制上下偏移。左下／右上检查两个方向分量，不是沿对角线计算一个总距离。

**特别注意：当前不是“鼠标拖到终点的瞬间必须卡拍”。** 玩家可以提前拖够距离，再保持按住等目标拍。点按与拖动的实际时间规则不同。

当前对照：退回／反向不会自动撤销，成功、失败、松手或重置会清除。

### 2.3 松手与失败恢复

- 未成功前松手：清除持握和准备状态；若已触发镜头偏移，播放失败回弹。
- 单独松手不直接增加挣脱格数；真正错过目标拍才计漏拍。
- 失败后，当前操作不推进，换一个目标拍重试。
- 失败统一清掉旧准备状态和旧鼠标起点，避免同一次失败拖动立即重复触发。
- 已触发镜头偏移的失败，有约 0.22 秒的回弹恢复期；期间鼠标移动不算新手势。
- 恢复期结束后，以新位置重新计位移；仍可保持左键按住，不要求再点一次。

## 3. 节奏规则与难度

### 3.1 时钟与目标拍

- BGM 当前为运行时生成的临时音乐，默认 112 BPM，一拍约 0.536 秒。
- 判定和节拍提示使用同一音频 DSP 时钟，并有声音输出延迟补偿；不以镜头动效结束或物体动画帧作为判定依据。
- 初始目标拍：当前音乐拍数向后至少预留 1 拍，再取整拍。因此实际准备时间通常在约 1～2 拍之间，不固定是整整 1 拍。
- 每一步正常推进后，目标拍加 1。自动演出步骤也占用流程中的拍位。
- 失败后，当前操作重新分配到当前音乐拍数之后的下一整拍；不会回滚 BGM。
- 当前没有 Perfect／Good 多档评分，主要使用成功／太早／太晚／漏拍反馈。

- 拖动时可以有镜头预反馈；角色和窗帘的成功动作由成功判定触发。

#### 🟨 P10：输入、演出与音效衔接
玩家开始有效操作时，窗帘出手动作与轻微镜头反馈立即响应，不等待成功判定。
判定成功后，衔接击中、NPC 受击和巴掌音效，不重新从头播放出手动作。提前达到操作条件时，击中与音效在目标拍点触发；在判定窗口内稍晚完成时，确认成功后立即触发，允许略晚于拍点。
判定失败时，不播放成功击中、NPC 受击或巴掌音效；已经开始的出手动作以打空或回弹收尾。完全没有操作时，只显示漏拍反馈，不凭空播放出手动作。失败反馈不要求严格落在拍点。
成功后立即更新当前操作提示与下一步预告，不等待旧动画结束。连续操作应流畅衔接，避免因演出阻塞输入。
优先保证操作跟手、成功击中有节奏感、失败结果清楚。具体动画时长、衔接方式和音效资源由程序与动画制作提出方案，结合试玩调整，不在本阶段锁定数值。
当前实现对照： 开始拖动时已有镜头预反馈，成功后角色出手；尚未实现上述“出手立即响应、判定后分支衔接”的完整方案，正式动画与完整音效表也尚未完成。

## 5. 连续漏拍与挣脱圆环

这是“连续漏拍恢复机制”，不是整轮累计失误分数。

| 连续漏拍数 | 圆环显示 | 结果 |
|---|---|---|
| 0～1 | 0/4 | 可以继续当前操作 |
| 2～3 | 1/4 | 压力上升 |
| 4～5 | 2/4 | 压力上升 |
| 6～7 | 3/4 | 压力上升 |
| 8 | 4/4 | NPC 挣脱，结束当前挑战 |

- 任意一次手动操作判成功：连续漏拍数及圆环立即清零，包括尚未凑成一格的单次漏拍。
- 自动过场：既不增加，也不清零；完成／挣脱演出不再计数。
- 太早点按或未成功前松手，不直接计一格；等目标拍真正错过再计漏拍。
- 同一目标拍不会因多个失败处理入口重复计数。
- 帧时间异常跨过多个完整的漏拍窗口时，当前代码会补计这些空拍，而不是只计一次。
- 新一轮和整轮重置清零；退出挑战后不继续增加。
- 普通／简单当前共用“每两拍一格、八拍挣脱”，难度差别只在判定窗口和移动距离等输入参数。

例子：漏一拍 → 又漏一拍 → 圆环 1/4 → 下一次操作成功 → 清零；之后漏一拍仍为 0/4，不继承之前的漏拍。

## 7. 面向模块化开发的初版约定

此节是交接目标，不代表当前代码已经完成模块化。

### 7.1 分清四层

| 层 | 负责什么 | 不应该负责什么 |
|---|---|---|
| 基础输入 | 按下／按住／松开、相对位移、方向、准备状态 | 直接推进窗帘步骤或决定 NPC 挣脱 |
| 节奏与流程 | 音频时钟、目标拍、判定、推进／重试、连续漏拍 | 直接写某个箭头或某种模型动画 |
| 拍谱配置 | 步骤顺序、输入类型、方向、占拍、衔接、表现引用 | 复制一份独立鼠标检测逻辑 |
| 表现 | 提示、演出、镜头、音效 | 通过动画结束反过来判输入成功 |

### 7.1.1 以窗帘为样例完善通用模块

模块化不是只拆鼠标代码。窗帘已经验证了下列系统需求，交接时应一起整理，但不同恶作剧是否启用、采用哪些参数，由各自配置决定；本版不设计其他恶作剧。

| 通用模块 | 窗帘样例 | 与其他模块的边界 |
|---|---|---|
| 基础输入库 | A01／A03 已用；A02／A04 按策划保留定义 | 不根据当前窗帘的实现删减基础输入 |
| 节奏时钟与判定 | 共用 DSP 时钟、普通／简单窗口、拖动准备结算 | 提供拍点与判定结果，不依赖提示动画或演出结束 |
| 流程／拍谱 | 二十步骤，手动与自动，成功推进、失败重试 | 步骤数据引用输入类型，不复制输入判断 |
| 节拍辅助 | 顶部圆／细线，默认关闭 | 只表达拍点；显隐不影响判定 |
| 可交互提示表现 | E 白圈、窗帘轻微挑动 | 接收可交互状态；不在提示组件内部实现物品选择逻辑 |
| 操作提示与预告 | 当前大圆、下一步小圆、自动步骤空图标 | 读取当前／下一步配置，不参与输入成功判断 |
| 难度与调参 | 普通／简单距离和窗口 | 参数集中维护；不要在各输入模块重复硬编码 |
| 演出调度 | 成功出手、自动靠近、成功离开、挣脱离开 | 与流程解耦，允许旧演出收尾时显示下一操作 |
| 镜头反馈 | 输入预偏移、失败回弹、成功缩放、压力缩放 | 响应输入／结果／进度事件；各层反馈不能互相误触发 |
| 连续漏拍恢复规则 | 两拍一格、成功清零、八拍挣脱、自动步骤排除 | 这是窗帘当前策略；通用接口可复用，不强制全游戏都使用此门槛 |
| 重置与诊断 | 清理旧手势、自动整轮记录 | 退出／重开统一清理状态；诊断不是玩家玩法 |

重构目标是这些模块能通过约定的状态与事件合作，不是把大脚本机械分成几个文件。基础输入 → 判定 → 流程结果；提示、演出、镜头读取相应事件。不得让“圆圈跳完了”或“动画播完了”反过来决定输入是否成功。

### 7.2 说明文档与配置的分工

本项目采用“规则说明＋可编辑配置”的方向：说明文档负责讲清规则与边界，配置负责排列已有能力和调整参数。不能只交一张数值表，让程序或 AI 猜判定含义；也不能把所有可变内容留在代码里，每次换一拍都重新写逻辑。

| 内容 | 放在哪里 | 例子 |
|---|---|---|
| 规则语义与边界 | 本 MD；确认后由程序实现 | 相对鼠标起点、成功如何推进、自动步骤为何不计漏拍 |
| 步骤编排 | 操作编排配置 | 这一拍点按还是拖动、方向、顺序、自动演出占拍 |
| 难度与容错参数 | 共用调参配置 | 普通／简单的判定窗口和距离阈值 |
| 表现参数与资源引用 | 反馈配置 | 图标、镜头幅度、动效时长、演出引用 |
| 新增输入识别能力 | 说明补齐后开发代码 | 实现尚不存在的路径分段识别；不是填一个名称就能启用 |

策划改配置，程序维护配置可支持的能力和校验。规则发生变化时先修改说明与验收条件；只调整既有范围内的数值或编排时，再改配置并试玩验证。

|---|---|---|
| 节奏 | BGM 引用、BPM、拍点偏移 | 判定与提示读取同一时钟；换音乐不能只改视觉速度 |
| 难度 | 点击窗口、定向移动阈值、其他已定义输入的难度参数 | 普通／简单各一组；未实现类型不填假参数冒充支持 |
| 重试 | 失败恢复时长、持握／起点重置策略 | 是否可调与具体语义须先确认，不能靠数值改变规则含义 |
| 窗帘漏拍策略 | 每格漏拍数、总格数、成功清零、自动步骤排除 | 当前为两拍一格、四格；策略可复用但不强制所有实例开启 |
| 提示 | 图标映射、主／预告尺寸与偏移、预告透明度、节拍弹跳参数 | 顶部辅助显隐是独立设置；不关闭当前操作提示 |
| 镜头 | 输入偏移上限、平滑时间、点按缩放、最终一击、压力缩放及恢复 | 各反馈分层；不得让成功清压力误取消成功动作反馈 |
| 演出与音效 | 各动作资源／反馈引用、衔接参数 | 未制作资源注明缺失，不视为已经完成 |

这是逻辑分组，不要求创建七份配置文件。首阶段可以用少量配置资源承载，避免为了模块化增加不必要的编辑负担。

### 7.2.3 配置校验与缺省行为

- 步骤 ID 唯一；下一步引用必须有效；流程不能意外陷入没有退出条件的循环。
- 手动步骤必须使用系统已支持的输入类型；不支持的 A02／A04 在编辑／加载时明确报错，不按 A03 凑合运行。
- 方向、路径分段等字段只在相应输入类型中有效；无关字段不能暗中影响判定。
- 持续拍数、窗口和距离有明确单位与合法范围；难度引用缺失、非法数值应给出可定位到步骤的错误。
- 图标原则上跟随输入与方向映射；若允许手动覆盖，必须避免“提示向左、判定向右”。自动步骤空图标是合法状态，不应补小点。
- 核心规则配置错误应阻止挑战启动并报告原因；缺失非必要美术反馈可提示警告。不要静默猜测玩法。

### 7.2.4 实施顺序与交接责任

1. 策划和程序先确认黄色项中的输入、拍谱、重试边界；未确认部分保留当前窗帘行为，不自行扩展。
2. 程序先把现有 A01／A03、自动步骤和二十步窗帘迁移到配置驱动；提示、预告、判定和演出读取同一流程状态。
3. 策划实际改一项操作、方向和重复次数，用第 7.3 节验收“改配置就能变玩法”，而不是仅仅多了几个配置文件。
4. A02／A04 的正式节奏规格确认后再开发；保留输入库定义不等于首轮必须一次实现全部类型。
5. 试玩调整共用参数，记录改动理由；之后再评估是否需要 Excel 工作流或更复杂的编辑器。

以上是建议开发顺序，不是本次已执行的重构。本次只整理文档。

## 8. 实现差异与已知边界

### 8.1 不要照旧文字恢复玩法

⚠️ 最后一步内部仍叫 `ThrowRightRelease`，提示文字仍有“甩出后松开”，但实际成功条件是按住并完成右上位移，在目标拍结算；不要求松开才能成功。本版以实际代码与近期试玩约定为准。

⚠️ “蓄力”目前是动作表现名称，不是独立的按住计时机制。

⚠️ 来源必须区分：网页“基础操作”最终版本定义通用四类输入，必须保留；网页的旧窗帘演出与 README 中过期流程不覆盖 Unity 窗帘实例。只在窗帘拍谱中排除旧的单独松手、额外挣扎拍等内容，不能连带删除基础库的“按住与松开”。

### 8.2 验证与工程边界

- 当前主要逻辑仍在一个运行时原型脚本中，有分函数和流程数组，但输入、流程与表现没有完成可复用模块拆分。
- A02 按住与松开、A04 路径移动已经是策划案的基础类型，但当前 Unity 尚未完成独立模块及正式节奏接入；手柄映射／震动、完整音效与正式动画资产也不列为已实现。
- 当前存在真实长帧记录，具体来源未解决；此前修复了失败后的旧手势重复触发，但不能等同于已经解决整帧卡顿。
- 已有自动整轮诊断记录，可以用于分析输入、判定、镜头与帧时间；调试记录不属于玩家玩法，不上传本地日志。
- 本文没有修改玩法代码，没有将待确认项变为程序需求；讨论确认后再更新版本。

## 9. 本轮讨论建议顺序

1. **先定 P03、P04**：拖动到底怎样卡拍，准备后反向是否取消。它们直接决定基础操作模块。
2. **再定 P08、P09**：窗帘拍谱与蓄力是否要计时。
3. **再定 P05、P11、P12**：失败恢复、漏拍容错、下一步预告。
4. **最后调 P06、P07、P10、P13**：音乐、难度数值、演出衔接和反馈幅度。
5. **P01、P14 作为通用模块补全讨论**：基础四类按策划保留；需要补的是各类边界、节奏参数、配置与接口，不是重新讨论它们是否存在。不要因为窗帘尚未使用就删掉，也不要让 AI 自行补一套未确认的判定。

## 10. 一起查漏补缺的讨论清单
